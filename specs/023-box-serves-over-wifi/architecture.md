# Architecture: Spec 023

## Overview

```
                         core 0                                          core 1
 /data/network.json ─┐
 /data/wifi.json ────┴─ main: network::boot_lines_radio, network::wifi_settings
                         │  EspWifi (station, PS off, host name solite-xxxxxx)
                         │  EspSntp (pool.ntp.org + DHCP's)          engine thread (spec 021)
                         │  console thread (UART0 lines) ───stop───▶  load_home → Arc<Mutex<Home>>
                         │    network::parse_console_line             radio, network, boot window
                         │                                            Saver gate: saves held until clock (≤ 20 s)
                         │◀──────── Shared { home, live hub } ──────── (mpsc channel)
                         │                                            radio + engine::run
                         ▼
             EspHttpServer :80 (server task)
             ├─ /ws  ──────────── live_ws.rs (registered directly, D36): post-handshake callback:
             │                    Host, Origin, LiveHub::connect, welcome; frames: subscribe
             │                    live thread: every 200 ms begin_batch/pop → httpd_queue_work
             ├─ / , /assets/* ─── core api::static_reply (Host, 405, route) → ui_files (flash, gzip)
             └─ everything else ─ Slots (4) → async request → queue (≤ 4) → worker thread
                                   (stack 10 KB + body buffer 16 KB, both PSRAM)
                                   → core api::handle_stream(reach = Lan{name})
                                   → Whole | List (chunks) | Order (wait) | ...
```

The core keeps every rule (the Wi-Fi settings, the retries, the reasons, the console's line rules,
the `Host` rule, the origin rule, the static headers, the slots, the pairing route's refusal on the
box), built and tested on the Mac by spec 022; this spec gives them ESP-IDF. It adds three small
core pieces, each tested on the Mac, where the firmware could not reach or hold a rule:

- `api::static_reply(&Request) -> Option<Reply>` (`crates/core/src/api/mod.rs`): `None` off the
  interface's paths; else `host_allowed` (403), then `static_files::route` (405, 404, the file), in
  the order of `dispatch` (l.231-244). `route` stays `pub(super)` (`static_files.rs` l.67) and
  `dispatch` is unchanged.
- The saver's gate (`crates/core/src/engine/saver.rs`): `Saver::with_gate(impl Fn() -> bool +
  'static)`; while closed and not stopping, `tick` returns `Ok(())` before taking any cursor, so no
  file is marked written or failed and `retry_at` is not moved; a stop ignores it.
- `WifiSettings::to_json(&self) -> String` (`crates/core/src/network.rs`): the text the console
  writes to `wifi.json`, read back to the same settings by `wifi_settings`.

The host is unchanged (it keeps `dispatch`, and no gate on its saver).

## Data

| Name | Type, unit | Where | Bound |
| ---- | ---------- | ----- | ----- |
| `/data/wifi.json` | `{"ssid": string, "password": string}` | the box's FAT partition, written by the console | spec 022's bounds (`MAX_WIFI_BYTES` 256, ...) |
| `WifiSettings`, `ConsoleCommand`, `Backoff`, `Reach`, `Slots`, `STATIC_HEADERS`, `live::session` | core types and rules | core, spec 022 | spec 022's |
| `ui_files` table | `&'static [(&'static str, &'static [u8])]`, sorted by path | `OUT_DIR/ui_files.rs`, generated by spec 022's `crates/ui-embed` from `firmware/build.rs`, bytes in flash | `MAX_UI_FILES` 32, 1 MB per file before compression; today 3 assets and `index.html`, about 54 KB gzip |
| `HeapStats.http_stack` | bytes, the smallest high-water mark of the 4 workers | filled by the firmware, printed by the core's `heap_line` (spec 022) | |
| Saver gate | `Box<dyn Fn() -> bool>` in `Saver`, `None` by default | core; the firmware's reads an `AtomicBool` (`CLOCK_SET`) set by SNTP's callback or the 20 s timer | one per saver |
| Workers' queue | the requests handed by the server's task to the workers | firmware `http_server.rs`, `sync_channel(MAX_WORKERS)` | 4 (`api::MAX_WORKERS`, `crates/core/src/api/slots.rs` l.9): `Slots` admits at most 4 in progress, so the queue never holds more and the server's task never waits on it |
| Console line | bytes | firmware, a 513-byte buffer on the console thread (the rest of a longer line discarded up to `\n`) | `MAX_CONSOLE_LINE` + 1 |
| Body buffers | 4 × `BODY_BUFFER_BYTES` (`MAX_BODY_BYTES` + 1 = 16 385 bytes) | firmware `http_server.rs`, one per worker, `heap_caps_malloc(.., MALLOC_CAP_SPIRAM)` at the server's start, kept for its life | 64 KB of PSRAM |
| Live sessions | session fd, client id, a `closed` flag shared with the session context ESP-IDF keeps with the socket, the message being received (≤ 1 KB) | firmware `live_ws.rs`, a `Vec` reserved for `MAX_CLIENTS` at start, behind a mutex; an entry removed when ESP-IDF releases the session context | `live::MAX_CLIENTS` 4 |

Constants named in the firmware: `CLOCK_WAIT_MS` 20 000, `WORKER_STACK_BYTES` 10 KB (PSRAM),
`BODY_BUFFER_BYTES` 16 385 (PSRAM, one per worker), `SERVER_STACK_BYTES` 8 KB, `CONSOLE_STACK_BYTES` 4 KB, `LIVE_STACK_BYTES` 4 KB, `MAX_OPEN_SOCKETS`
12, `RESTART_WAIT_MS` 10 000, `HTTP_PORT` 80.

### ESP-IDF settings added to `firmware/sdkconfig.radio.defaults` (radio image only)

| Setting | Value | Why |
| ------- | ----- | --- |
| `CONFIG_HTTPD_WS_SUPPORT` | `y` | `/ws` (ESP-IDF's WebSocket support is gated by it) |
| `CONFIG_HTTPD_WS_POST_HANDSHAKE_CB_SUPPORT` | `y` | the checks and the welcome of a new `/ws` client run in this callback: ESP-IDF 5.5 calls the URI handler for the frames only (D36, added after the run on the box) |
| `CONFIG_HTTPD_MAX_REQ_HDR_LEN` | `1024` | a browser's head is about 500 to 800 bytes; 512 by default |
| `CONFIG_LWIP_MAX_SOCKETS` | `16` | 10 by default; ESP-IDF's server needs `max_open_sockets` + 3 (its listener and two UDP control sockets) and `httpd_start` refuses fewer (`httpd_main.c` l.495-507): 12 + 3 = 15, one spare; DHCP, DNS and SNTP use lwIP's raw API, no socket; about 40 B static per slot, about 0.4 KB per open socket (estimate, R9.5) |
| `CONFIG_LWIP_TCPIP_TASK_AFFINITY_CPU0` | `y` | lwIP's tcpip task on core 0 (no core by default), off the engine's core 1 (R4.1) |
| `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY` | `y` | the 4 workers' stacks in PSRAM (`esp_pthread_cfg_t.stack_alloc_caps` = `MALLOC_CAP_SPIRAM`), on from the start (R9.4); no task with a PSRAM stack writes the flash |
| `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP` | `y` | Wi-Fi and lwIP buffers in PSRAM when they can be (spares internal RAM) |
| `CONFIG_LWIP_DHCP_GET_NTP_SRV` | `y` | the DHCP server's time server, when it gives one |
| `CONFIG_LWIP_SNTP_MAX_SERVERS` | `2` | `pool.ntp.org` and the DHCP one |
| `CONFIG_ESP_CONSOLE_UART_DEFAULT` | (default, kept) | the console stays UART0 at 115200, the log's port |
| `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL` | `2048`, **only if R9.3 calls for it** | not set at first (the 4096 of `sdkconfig.defaults` holds); the knob approved by the user, written here when a figure falls under 64 KB, then measured again |

`sdkconfig.defaults` is not touched: the box, sim and measuring images keep their settings and their
measured figures (as spec 021 did with `CONFIG_UART_ISR_IN_IRAM`). `validate.sh` checks that
`CONFIG_HTTPD_WS_SUPPORT=y` is in the radio build's `sdkconfig` and in no other.

## Risks

- ESP-IDF's asynchronous requests are not wrapped by `esp-idf-svc` 0.53: the worker code calls
  `httpd_req_async_handler_begin`/`complete`, `httpd_req_recv`, `httpd_resp_*` through
  `esp_idf_svc::sys` (the raw request comes from `EspHttpRawConnection`'s `RawHandle`). If it proves
  unusable, the fallback is to answer on the server's task, an order then holding it up to 12 s: that
  fallback needs the user's yes (it changes R4.3).
- `esp-idf-svc` 0.53 gives no header of a WebSocket request, and on the box (2026-11-22) its
  `ws_handler` never saw the handshake: ESP-IDF 5.5 calls a WebSocket URI handler for the frames
  only, so no session was made and a browser got its 101 and nothing more. `/ws` is therefore
  registered directly with ESP-IDF (D36): `Host` and `Origin` are read in the post-handshake
  callback, while the handshake's request is valid, with `httpd_req_get_hdr_value_str` in one
  `unsafe` function with its `SAFETY` comment (D11); the refusal codes are unchanged.
- Reading UART0 while it is ESP-IDF's console needs its driver installed and the VFS switched to it;
  if the log and the console disturb each other, the console moves to a line prefix the log never
  prints.
- LRU closing at 12 connections may close a live client; it reconnects (the interface retries).
- No software coexistence between the two 2.4 GHz chips: a Wi-Fi channel over the Zigbee channel
  may cost Zigbee messages; seen in the log, not solved here.
- The internal RAM: with the budget's 70 KB for Wi-Fi and the 16 KB of stacks that stay internal,
  the network's cost is about 86 KB and the projection for the realistic home about 21 KB, under
  the 64 KB floor even with the workers' stacks in PSRAM (R9.4); the run's own minimum likely
  passes. The cost is measured as 234 KB (spec 021's `heap:` minimum, one device) minus the run's
  first `heap:` minimum (R9.1), not from the `memory-network:` snapshot. R9.3 says what happens:
  `SPIRAM_MALLOC_ALWAYSINTERNAL` 2048 in the radio image (approved by the user), measured again,
  then stop and report if still short.
- The saver's gate: a stop during the clock wait writes the files with the clock as it is (1970
  dates possible), by design (R3.2); the gate never holds a stop.
- The radio image's size: about 930 KB today in a 4096 KB slot; Wi-Fi, the server and the interface
  are estimated at 0.55 to 0.75 MB more (R7.5). Beyond the slot: stop and report (R7.5).
- PSRAM stacks: a task whose stack is in PSRAM must never write the flash (the cache is off during
  the write); the workers only lock the home and answer, the saves stay on the engine thread, and
  the console (which writes `wifi.json`) keeps an internal stack.
