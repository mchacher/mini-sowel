# Architecture: Spec 023

## Overview

```
                         core 0                                          core 1
 /data/network.json ─┐
 /data/wifi.json ────┴─ main: network::boot_lines_radio, network::wifi_settings
                         │  EspWifi (station, PS off, host name solite-xxxxxx)
                         │  EspSntp (pool.ntp.org + DHCP's)          engine thread (spec 021)
                         │  console thread (UART0 lines) ───stop───▶  load_home → Arc<Mutex<Home>>
                         │    network::parse_console_line             radio, network, boot window
                         │                                            saves held until clock (≤ 20 s)
                         │◀──────── Shared { home, live hub } ──────── (mpsc channel)
                         │                                            radio + engine::run
                         ▼
             EspHttpServer :80 (server task)
             ├─ /ws  ──────────── live_ws.rs: Host, Origin, LiveHub::connect, subscribe
             │                    live thread: every 200 ms begin_batch/pop → detached sender
             ├─ / , /assets/* ─── core static_files::route → ui_files table (flash, gzip)
             └─ everything else ─ Slots (4) → async request → worker thread
                                   (stack 10 KB + body buffer 16 KB, both PSRAM)
                                   → core api::handle_stream(reach = Lan{name})
                                   → Whole | List (chunks) | Order (wait) | ...
```

The core keeps every rule (the Wi-Fi settings, the retries, the reasons, the console's line rules,
the `Host` rule, the origin rule, the static headers, the slots, the pairing route's refusal on the
box), all built and tested on the Mac by spec 022; this spec gives them ESP-IDF. No core or host
file changes here, but for the doc comment of `network::boot_lines`.

## Data

| Name | Type, unit | Where | Bound |
| ---- | ---------- | ----- | ----- |
| `/data/wifi.json` | `{"ssid": string, "password": string}` | the box's FAT partition, written by the console | spec 022's bounds (`MAX_WIFI_BYTES` 256, ...) |
| `WifiSettings`, `ConsoleCommand`, `Backoff`, `Reach`, `Slots`, `STATIC_HEADERS`, `live::session` | core types and rules | core, spec 022 | spec 022's |
| `ui_files` table | `&'static [(&'static str, &'static [u8])]`, sorted by path | `OUT_DIR/ui_files.rs`, generated by spec 022's `crates/ui-embed` from `firmware/build.rs`, bytes in flash | `MAX_UI_FILES` 32, 1 MB per file before compression; today 3 assets and `index.html`, about 54 KB gzip |
| `HeapStats.http_stack` | bytes, the smallest high-water mark of the 4 workers | filled by the firmware, printed by the core's `heap_line` (spec 022) | |
| Console line | bytes | firmware, a 513-byte buffer on the console thread (the rest of a longer line discarded up to `\n`) | `MAX_CONSOLE_LINE` + 1 |
| Body buffers | 4 × `BODY_BUFFER_BYTES` (`MAX_BODY_BYTES` + 1 = 16 385 bytes) | firmware `http_server.rs`, one per worker, `heap_caps_malloc(.., MALLOC_CAP_SPIRAM)` at the server's start, kept for its life | 64 KB of PSRAM |
| Live sessions | session fd, detached sender, client id | firmware `live_ws.rs`, a fixed array | `live::MAX_CLIENTS` 4 |

Constants named in the firmware: `CLOCK_WAIT_MS` 20 000, `WORKER_STACK_BYTES` 10 KB (PSRAM),
`BODY_BUFFER_BYTES` 16 385 (PSRAM, one per worker), `SERVER_STACK_BYTES` 8 KB, `CONSOLE_STACK_BYTES` 4 KB, `LIVE_STACK_BYTES` 4 KB, `MAX_OPEN_SOCKETS`
12, `RESTART_WAIT_MS` 10 000, `HTTP_PORT` 80.

### ESP-IDF settings added to `firmware/sdkconfig.radio.defaults` (radio image only)

| Setting | Value | Why |
| ------- | ----- | --- |
| `CONFIG_HTTPD_WS_SUPPORT` | `y` | `/ws` (`esp-idf-svc`'s `ws_handler` is gated by it) |
| `CONFIG_HTTPD_MAX_REQ_HDR_LEN` | `1024` | a browser's head is about 500 to 800 bytes; 512 by default |
| `CONFIG_LWIP_MAX_SOCKETS` | `24` | 12 connections, the listener, the server's control socket, DNS, SNTP, DHCP, and room so the LRU close at 12 never meets an internal socket (ESP-IDF needs `max_open_sockets` ≤ this − 3); about 40 B static per slot, about 0.4 KB per open socket (estimate, R9.5) |
| `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY` | `y` | the 4 workers' stacks in PSRAM (`esp_pthread_cfg_t.stack_alloc_caps` = `MALLOC_CAP_SPIRAM`), on from the start (R9.4); no task with a PSRAM stack writes the flash |
| `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP` | `y` | Wi-Fi and lwIP buffers in PSRAM when they can be (spares internal RAM) |
| `CONFIG_LWIP_DHCP_GET_NTP_SRV` | `y` | the DHCP server's time server, when it gives one |
| `CONFIG_LWIP_SNTP_MAX_SERVERS` | `2` | `pool.ntp.org` and the DHCP one |
| `CONFIG_ESP_CONSOLE_UART_DEFAULT` | (default, kept) | the console stays UART0 at 115200, the log's port |

`sdkconfig.defaults` is not touched: the box, sim and measuring images keep their settings and their
measured figures (as spec 021 did with `CONFIG_UART_ISR_IN_IRAM`). `validate.sh` checks that
`CONFIG_HTTPD_WS_SUPPORT=y` is in the radio build's `sdkconfig` and in no other.

## Risks

- ESP-IDF's asynchronous requests are not wrapped by `esp-idf-svc` 0.53: the worker code calls
  `httpd_req_async_handler_begin`/`complete`, `httpd_req_recv`, `httpd_resp_*` through
  `esp_idf_svc::sys` (the raw request comes from `EspHttpRawConnection`'s `RawHandle`). If it proves
  unusable, the fallback is to answer on the server's task, an order then holding it up to 12 s: that
  fallback needs the user's yes (it changes R4.3).
- Reading UART0 while it is ESP-IDF's console needs its driver installed and the VFS switched to it;
  if the log and the console disturb each other, the console moves to a line prefix the log never
  prints.
- LRU closing at 12 connections may close a live client; it reconnects (the interface retries).
- No software coexistence between the two 2.4 GHz chips: a Wi-Fi channel over the Zigbee channel
  may cost Zigbee messages; seen in the log, not solved here.
- The internal RAM: with the budget's 70 KB for Wi-Fi the projection for the realistic home is
  about 37 KB before the server's stacks, about 21 KB after the 16 KB that stay internal, under the
  64 KB floor even with the workers' stacks in PSRAM (R9.4); the run's own minimum likely passes.
  R9.3 says what happens: stop and report, the next knob proposed.
- The radio image's size: about 930 KB today in a 4096 KB slot; Wi-Fi, the server and the interface
  are estimated at 0.6 to 0.8 MB more. Beyond the slot: stop and report (R7.5).
- PSRAM stacks: a task whose stack is in PSRAM must never write the flash (the cache is off during
  the write); the workers only lock the home and answer, the saves stay on the engine thread, and
  the console (which writes `wifi.json`) keeps an internal stack.
