# Architecture

How Solite is built **today**. Short: the blocks, where they run, how data flows. Only what
exists: the target architecture is decision D1, and what comes next is in the roadmap.

## Overview

```
          crates/core  (Rust library: name, version, banner, memory line;
                        radio/: ASH, EZSP, ZDO, ZCL, the coordinator;
                        engine/: the radio loop and the saver; no socket, no
                        clock, no random source, no file)
                  │                         │
     crates/host (Rust, Mac)          firmware/ (Rust std on ESP-IDF, ESP32)
     prints the banner; with          banner, memory, data partition (FAT),
     --radio, TCP transport ──► Dongle Max's radio (original firmware, port 6638)
     files in a folder                network setting; feature sim: the engine on
                                      crates/sim; booted on the Mac in
                                      Espressif's QEMU (scripts/qemu.sh);
                                      feature radio: the engine on the real radio
                                      over UART1 (the radio image)

     ui/ (Preact + TypeScript, browser): the rooms and equipments, live;
         served from ui/dist by the host's --serve, or from the radio
         image's flash, through /api and /ws

     tools/z2m-coverage (Node, Mac only): Zigbee2MQTT's library → report.md
```

The core has no hardware or operating-system dependency: the same code is compiled for the Mac
(`aarch64`/`x86_64`) and for the ESP32 (`xtensa-esp32-espidf`). The interface is a separate web
app, built by Vite into `ui/dist`, which the host's `--serve` serves from disk and the radio image embeds, compressed, in its flash.

## Blocks

| Block | Role | Where in the code |

| Core | The Sowel core: shared by every program, no hardware. `radio/`: the ASH frame layer, the EZSP commands and callbacks, ZDO and ZCL frames, the generic reading of the standard clusters' measures (`measures.rs`), and the coordinator (start or resume the network, pairing, identifying a device, setting up its reporting, enrolling alarm devices, listening to its measures, sending commands and waiting for their acknowledgement in `commands.rs`), as state machines fed with bytes, time and random bytes; | Backup | In the core: `backup/` (`mod.rs`: the bounds, the fixed list of names, the `BackupFiles` adapter trait (live, staged `.restore` and `.new` files, the marker `restore.pending`, the one-shot mark `zigbee.restore`, the set-aside of another network's keys) and the `Pacing` trait (clock and 10 ms pause); `format.rs`: header, entry and manifest; `crypto.rs`: PBKDF2 in slices that pause every 5,000 iterations, ChaCha20 per entry and HMAC-SHA256, with the `chacha20` crate (RustCrypto, pure Rust, no AEAD in the dependencies, decision D56); `export.rs`: `ArchiveReader`, an `io::Read` that streams the archive in 4 KB chunks; `restore.rs`: the restore, validated whole into staged copies and committed through the marker, and `apply_pending`, which every start calls first, before the data is read); `home/` holds the backup state (idle, preparing, exporting, restoring, pending, plus the Saver's `writing` mark; its own lock) that the gate, the tickets and the `Saver` share, so the Saver writes nothing while an export reads the files; `api/mod.rs` answers `GET` and `POST /api/v1/system/backup` with `Reply::BackupExport` and `Reply::BackupRestore` (a ticket whose `export` and `restore` do the jobs) **without reading the body** (`api::is_streamed_request` lets the caller ask first; through the plain `handle` both are 501). The servers only move bytes: the host's `serve.rs` (`tiny_http`, chunked body) and the firmware's HTTP server (`send_chunk`, then the restart after a restore as the update's) with their `BackupFiles` adapters over `solite-data/` (the archive's `zigbee.json` is the host's `network.json`) and `/data`, decision D56 | `crates/core/src/backup/`, `crates/core/src/api/mod.rs`, `crates/host/src/{backup,backup_files,serve}.rs`, `firmware/src/{backup_files,http_server}.rs` |
| Updates | In the core: `update/` (`mod.rs`: the 128-byte signed header, the key given as a value, the `UpdateAdapter` trait, `Updates` and its `install`; `install.rs`: the streaming of the image, 4096 bytes at a time, into the adapter, hashed on the way; `probation.rs`: the verdict of a newly booted image from the monotonic time and the health, confirm after 60 s healthy, roll back after 300 s without), which verifies only, with `ed25519-dalek` (no precomputed tables; the core's one dependency for it, decision D52) and the `sha2` the core already has; `api/mod.rs` answers `POST /api/v1/system/update` with `Reply::Update` once the gate and the content type pass, **without reading the body**, which the caller streams into `Updates::install` (`api::is_update_request` lets it ask first; through the plain `handle` the route is 501); `api/system.rs` serves `GET /api/v1/system/version`. In the host: `update_files.rs` (the file adapter on `<data>/update/`: two slots and `boot.json`, and `start_updates`, the start lines), `update_cli.rs` (`--update-keygen` and `--update-sign`, the only code that signs, with the signing part of `ed25519-dalek`) and `serve.rs` (the route streamed from the socket, the probation thread). In the firmware: the same `Updates`, an adapter on ESP-IDF's OTA (`esp-idf-svc`) whose flash calls and probation tick run on one thread with a stack in internal RAM; the key of both programs is the build-time `SOLITE_UPDATE_PUBLIC_KEY`, decisions D52 to D54 | `crates/core/src/update/`, `crates/core/src/api/{mod,system}.rs`, `crates/host/src/{update_files,update_cli,serve}.rs`, `firmware/src/ota.rs` |

In the firmware (radio image): the RTC record in `.rtc_noinit`, the adapter, the engine thread's task-watchdog subscription and the tick on the OTA thread's one-second loop; the host has the default status. | Host | The program on the Mac; `radio_tcp.rs` is the TCP transport to the Dongle Max's radio; `random.rs` reads the system's random source; `backup.rs` writes the network backup to the data folder (`solite-data/`, ignored by git) | `crates/host/` |
| Firmware | The program on the Dongle Max's ESP32: banner, memory line, the data partition mounted at `/data` (FAT with wear levelling, `storage.rs`; formatted when it does not mount), the network setting read from `/data/network.json`; the image of the box then logs `radio: none`; with the cargo feature `radio` (the radio image) it reads `/data/wifi.json`, starts the Wi-Fi station (retried forever, power save off) and SNTP (the engine's saves are held until the clock is set, 20 s at most), serves Sowel's API, `/ws` and the interface on port 80 (ESP-IDF's HTTP server, a pool of 4 workers with their stacks and 16 KB body buffers in PSRAM, the API through the core's `handle_guarded` and `static_reply` under `Reach::Lan`; the full backup's export and restore run on a `backup` thread started for the job, its 10 KB stack in internal RAM, because a stack in PSRAM cannot touch the flash, D59), runs a live thread (the 200 ms batches) and a console thread (the serial lines `wifi-set`, `wifi-forget` and `pair`, parsed by the core; its logic (the probe, the reset steps, the boot window, the restart of a wedged radio) is in the core's `radio/serial.rs`; with the cargo feature `sim` (the image QEMU runs) it seeds `/data` with the realistic home of `firmware/fixtures/` and runs the engine on the simulated radio in a thread of 32 KB of stack (`simulated.rs`), then logs the `engine:` line with the memory it measured (`measure.rs`, ESP-IDF's local-minimum monitor of the free heap); | Box | The Dongle Max over USB: `scripts/box.sh` identifies it, saves and restores its whole flash, flashes an image (the radio image can keep `storage`) and checks its boot log (and its count of flash writes against `--budget`), sends the Wi-Fi settings to the radio image's serial console (`wifi`), and runs one test with the saves held and flushed in one serial session (`saves`); `scripts/demo-garage.sh` and `scripts/measure-api.sh` drive an API on the Mac or on an address; `scripts/box-session.sh` runs a whole box session in one pass through `box.sh` (D55); `scripts/lib/firmware.sh` (tool lookup, partition table, application image, boot-log checks) is shared with `scripts/qemu.sh` | `scripts/box.sh`, `scripts/box-session.sh`, `scripts/lib/firmware.sh` |

## Builds

- **Mac workspace** (`Cargo.toml` at the root): `crates/core`, `crates/host`, `crates/sim`, `crates/ui-embed`; Rust stable pinned
  in `rust-toolchain.toml`.
- **Firmware** (`firmware/Cargo.toml`): built with the Xtensa toolchain from `espup`, target
  `xtensa-esp32-espidf`, ESP-IDF version pinned in `firmware/.cargo/config.toml`; the build
  downloads ESP-IDF into `firmware/.embuild/` (ignored by git). Settings of ESP-IDF:
  `firmware/sdkconfig.defaults` (16 MB flash, PSRAM in the heap with allocations above 4 KB
  placed there and 64 KB of internal RAM kept for the network and DMA, mbedTLS buffers in PSRAM,
  chip revision 3 and later, long file names on the FAT partition). The cargo feature `sim`
  builds the image QEMU runs (the simulator and the fixtures inside); `flash-saves` builds the
  measuring image, which `scripts/box.sh` flashes on the Dongle Max; `radio` builds the radio
  image, in its own target folder (`CARGO_TARGET_DIR=target/radio`) with
  `firmware/sdkconfig.radio.defaults` read after `sdkconfig.defaults` (the UART interrupt in
  internal RAM, the WebSocket and its post-handshake callback, the server's request head, the lwIP socket table of 16 and its
  core pinning, the PSRAM stacks and Wi-Fi and lwIP buffers, SNTP's servers), never together with
  `sim`; `firmware/build.rs` embeds `ui/dist` for `radio` only, through `crates/ui-embed`, so
  `ui/dist` is built before the radio image (`validate.sh` does it); `firmware/.cargo/config.toml` sets `CARGO_WORKSPACE_DIR` so the settings files and `.embuild` are found in `firmware/` whatever the target folder is; without them, the image is the box's. The partition table is `firmware/partitions.csv` (settings, two
  application slots of 4 MB, a data partition; decision D25), given to the box by `scripts/box.sh flash`, not
  through `sdkconfig.defaults`. `sh scripts/qemu.sh` builds that table, assembles a flash image
  with ESP-IDF's `esptool` with the application at the offset of the first slot, as the table
  gives it, and boots it in Espressif's QEMU (`qemu-system-xtensa`, installed into
  `firmware/.embuild/` by ESP-IDF's tool installer), with 2 MB of PSRAM, the data partition blank
  at every run; it fails on a panic, a reboot, a missing line, a heap peak of the engine above
  350 KB, a device of the home with no measure, a dropped radio callback or an internal RAM minimum free below 64 KB (`--box` boots the box's image instead). The wiring, the risks and the backup procedure of the box are
  in [hardware.md](hardware.md); the memory shared out item by item is in
  [memory-budget.md](memory-budget.md).
- **Update key**: `SOLITE_UPDATE_PUBLIC_KEY` (64 hex characters) is read at build time with
  `option_env!` by the host and the firmware; without it, a build refuses updates (503). The
  private key is never in the repository.
- **Unsafe code**: the core and the host forbid it; the firmware denies it, except in the small
  functions that call ESP-IDF's C functions, each with a `SAFETY` comment (decision D11).
- **Tools** (`tools/<name>/`): TypeScript run directly by Node 24, no build step; type-checked by
  `tsc`, tested with `node:test`.
- **Interface** (`ui/`): Vite builds `ui/dist/`, which the host serves and the radio image embeds; `npm run dev` proxies
  `/api` and `/ws` to a host on port 8080; `ui/scripts/check-bundle-budget.mjs` checks the
  first load against its budget.

## Data

The box's own image stores no data; the radio image keeps the engine's files, `zigbee.json` (the
network's backup, keys in plain text), `wifi.json` (the Wi-Fi name and password, in plain text, never in NVS), `auth.json` and its boot marker `booting` in `/data`. Between a restore and the next start, `/data` (and `solite-data/` on the Mac) also holds the staged copies `<name>.restore` of the files a restore replaces and the marker `restore.pending` that names them (the start applies them and removes both); a restored network leaves the one-shot mark `zigbee.restore` until the radio's network is up. On the Mac, the host keeps `zones.json`, `equipments.json`,
`recipes.json`, `settings.json` and `auth.json` (the account and its password hash, or `{"version":1}` without an account; written
within 2 seconds of a change under `--serve`), `devices.json` (Sowel's devices with their
data and orders, and each device's last network address and endpoint; definitions written within 2 seconds under `--serve`, at once with `--pair`, values every 10 minutes, everything on stop) and writes
`network.json` (the network's identifiers
and keys, mode 0600) to its data folder after forming a network; the radio keeps the network
itself in its own flash. Under `--serve`, the host also keeps its update slots in `update/` of the data folder (`slot-0.bin`, `slot-1.bin`, `boot.json`); the box keeps the images in its two application slots and the boot record in `otadata`. On the Mac, `tools/z2m-coverage/report.md` is the coverage
report, committed with the library version and date it measures.
